# docs-creator（项目文档库体系）

## Overview

一套开发者与 AI 共同维护的项目文档库：**权责分明、流程单向、全程可追溯**。

- 工作流：开发者写 `design.md`（需求正本）→ AI 严格依据它生成 `designs-specs.md`（开发直接依据）→ AI 按 specs 开发 → AI 记开发日志 → 产物按机制归档。
- 核心纪律：每类文档有唯一维护方（权责表）；归档只是移动、文件永不删除；AI 永不擅改开发者的需求正本。

**模式判定**（开始前先确认，拿不准就问开发者）：

- 项目没有 `docs/` 或文档散乱无体系 → **模式 A：全新搭建**
- 项目已有文档（自己的旧项目或别人的项目）→ **模式 B：盘点升级**——先盘点出映射提案，**开发者批准后**才迁移，不擅自移动/改名既有文档
- 二次开发别人的代码库、需要先吃透代码 → 模式 B 基础上**同时建 `docs/study/` 学习笔记体系**

**硬性前置（先于模式 A/B 一切动作，无条件执行）**：项目已存在 `docs/` 时，先把整个 `docs/` **原封不动重命名为 `doc/`**——只改文件夹名，内容零改动；用文件系统 `mv`，不用任何 git 命令。然后再按本 skill 新建 `docs/`。若 `doc/` 已存在，停下问开发者，绝不覆盖、合并或跳过。重命名后原库只读保留：后续盘点、迁移、提案一律不得改动 `doc/` 内文件。

## 目录结构

```
docs/
  log/                          # 开发日志，每天一个 YYMMDD.md（AI 维护）
    log.md                      # 目录说明（功能作用与使用介绍）
  project/                      # 项目文档库（开发者与 AI 共同维护）
    project.md                  # 目录说明 + 项目总介绍（开发者主导）
    README.md                   # spec/plan 存放与归档机制正本（AI 维护）
    新功能开发区.md              # 开发者记录新功能需求（AI 立项实施后按轮归档）
    优化建议区.md                # 开发者记录优化建议（AI 实施后按轮归档）
    问题疑惑区.md                # 开发者记录疑惑（AI 不主动查阅）
    临时草稿（待写入）.md        # 开发者草稿本（搭建时 AI 代建骨架，之后不读取）
    idea/                       # 开发者想法草稿（AI 只动自己产出的 spec/plan）
      idea.md                   # 目录说明（开发者领地，AI 不得擅改）
      <模块>/                   # idea 阶段模块的 spec/plan 暂存
    <区域>/                     # 已立项模块按界面分区或功能域分组（如 左侧边栏/、modules/）
      <区域>.md                 # 区域说明 + 跨模块硬性规则（如 左侧边栏/左侧边栏.md）
      <模块>/                   # 模块目录随其第一份 design.md 产生，不预建
        design.md               # 该模块需求正本（开发者主导）
        designs-specs.md        # AI 开发依据（AI 生成维护）
        YYYY-MM-DD-<主题>-design.md   # 单次功能的 brainstorming 设计记录（spec）
        YYYY-MM-DD-<主题>-plan.md     # 实施计划（plan，头部 **Spec:** 字段与 spec 互指）
        archive/                # 落地或废弃的 spec/plan 归档处
  study/                        # （可选）代码走读学习笔记：README 导读 + 编号章节
```

**目录说明文档约定**：docs/ 下每个子目录都有一份与目录同名的 `.md`（如 `log/log.md`、`project/project.md`、`idea/idea.md`、`<区域>/<区域>.md`），说明该目录的功能作用与使用方式；新建子目录时随建随补，维护方随该目录的权责归属。

全局性文档（样式规范、跨模块硬性规则、全局功能）按项目实际放 `docs/project/样式/`、`docs/project/全局/` 等同级目录，权责同模块 design.md / designs-specs.md。

## 权责表（体系的宪法）


| 内容                              | 维护方            | AI 的角色                                                                                  |
| ----------------------------------- | ------------------- | -------------------------------------------------------------------------------------------- |
| `project.md` 项目总介绍           | 开发者主导        | 可提建议；经审核通过才可协助完善                                                           |
| `<模块>/design.md` 需求正本       | 开发者主导        | **不得擅自改写**；可提建议或经审核协助                                                     |
| `<模块>/designs-specs.md`         | **AI 生成并维护** | 基于 design.md 严格生成；开发者仅简单审核                                                  |
| `docs/project/README.md` 机制正本 | AI                | 维护存放与归档机制并随演进更新                                                             |
| `docs/log/YYMMDD.md`              | AI                | 每天一个开发日志                                                                           |
| `优化建议区.md`                   | 开发者记录        | AI 据此实施；实施后按轮归档进该文档「归档区」                                              |
| `新功能开发区.md`                 | 开发者记录        | AI 据此 brainstorming 立项并实施；完成后条目勾选、按轮归档进该文档「归档区」               |
| `问题疑惑区.md`                   | 开发者记录        | **AI 不主动查阅**；开发者指明时才读并答疑，解答后按轮移入已完成区                          |
| `idea/` 与 `临时草稿.md`          | 开发者            | 草稿本骨架由 AI 搭建时**代建**（模板见 templates.md 第 12 节），建后不关注、不读取、不修改（例外：AI 产出的 spec/plan 可存`idea/<模块>/`，只动自己产出的文件） |
| 各子目录同名说明 md（`log.md` 等） | 随目录权责        | 说明该目录功能与用法；新建子目录时随建随补                                                 |
| Git 操作                          | 开发者            | **AI 禁止自主执行任何 git 操作**（add/commit/push/pull/checkout/reset 等全部命令）；最多在开发者明确要求时给出命令建议，不得代为执行 |

## 机制要点

**spec / plan**：命名 `YYYY-MM-DD-<主题>-design.md` / `-plan.md`，日期前缀保证唯一，归档不改名；spec 与 plan 同目录混放、头部互指；存放位置——idea 阶段模块入 `idea/<模块>/`，已立项入所属模块目录，跨模块/右栏类改动入对应区域目录。落地判定按项目约定（默认：typecheck/构建通过即算落地，不等人工冒烟；无构建流程的纯文档项目以开发者验收确认为准）。

**归档**（全自动，写日终日志、写新 spec/plan 时顺带清点；开发者说「归档一下」为兜底）：


| 判定                                        | 动作                                                                 |
| --------------------------------------------- | ---------------------------------------------------------------------- |
| 落地（日志/状态行记录实施完成）             | 移入所属目录`archive/`，状态行追加 `- 已归档：YYMMDD 随 <功能> 落地` |
| 废弃（**开发者明说才废弃**，AI 不自行判定） | 移入`archive/`，状态行标注 `- 已归档：YYMMDD 废弃（<原因>）`         |
| 待实现 / 进行中 / 依据不明                  | 不动；拿不准报告开发者                                               |

固定四步：① `mv` 入 `archive/` 不改名 → ② 文档顶部状态区追加归档行 → ③ 全库检索旧路径、更新**活动文档**引用（历史日志不改）→ ④ 当天日志记一笔。spec 归档时其对应 plan（`**Spec:**` 指向它者）一并归档；模块正式立项迁移目录时 spec/plan 一并迁入。回改通道：archive 内直接改或移回，日志记录；**归档只是位置变化，文件永不删除**。

**版本管理**：docs/ 文档库（含 log/、study/、归档）默认**纳入 git、随远程仓库维护**；**禁止把 `docs/` 或其任何子目录写进 `.gitignore`**。搭建/升级时若发现已有此类忽略规则，向开发者说明并提请移除；git 操作仍由开发者执行。

**开发日志**：`docs/log/YYMMDD.md` 每天一个由 AI 维护；**每个小节标题下必须附创建时间行**——`> 创建于 YYYY-MM-DD HH:MM`，用 `date` 命令取实际时间，不估不编。小节结构：标题（功能名 + 来源 + 范围）→ **需求** → **设计定稿**（含设计文档路径）→ **实施** → **验证** → **涉及文件**。

**新功能开发区 / 优化建议区 / 问题疑惑区按轮归档**：AI 每完成一轮，把该轮全部条目作为一组，在归档区/已完成区**顶部**新增 `### 第N轮（YYMMDD）：本轮主题` 小节；条目保留原始描述并附完成说明/立项说明/问答全文；轮次从第 1 轮起、全项目连续编号只增不减，新轮永远插最上方。

各文档骨架模板见 [templates.md](templates.md)——按项目适配后使用，示例内容不得原样照搬。

## 模式 A：新项目搭建步骤

1. 摸清项目定位：项目名、性质、技术栈、功能模块划分（读现有 README/代码，缺了问开发者）
2. 建骨架：`docs/project/` 共用正本（README.md、project.md〔兼目录说明，骨架供开发者填写〕、新功能开发区.md、优化建议区.md、问题疑惑区.md、**临时草稿（待写入）.md〔AI 按 templates.md 第 12 节模板代建骨架，条目全部留白，建后不再读取/修改〕**）与 `docs/log/`（含 log.md 目录说明）；`idea/` 与模块子目录**不预建**，随第一份对应文档产生，新建任何子目录时随建随补同名说明 md；确认 `.gitignore` 未忽略 `docs/`（已有则提请开发者移除——文档库默认随远程仓库维护）
3. 写 `docs/project/README.md`（机制正本，用模板适配项目命名习惯）
4. **写/更新项目 CLAUDE.md**——把权责表、工作流、全局硬性规则、Git 纪律写进去。这是体系运转的关键：CLAUDE.md 每次会话自动加载，不接线索体系不会被执行
5. **主动商讨模块划分与 design.md 归属**（基本文档建完后立即进行，不等开发者开口）：结合项目实际（代码/README）提出功能域目录规划（如 `notes/`、`todos/`、`vault/`、`全局/`），与开发者逐个确认归属与命名；再按项目阶段定 design.md 由谁初始化——**新项目**：开发者落笔，AI 只给模块清单与写作建议，不代写；**接管/继续开发项目**：经开发者委托，AI 通读代码后起草/补全各模块 design.md，交开发者审核定稿（审核权始终在开发者，不违背权责表红线）
6. 与开发者过一遍权责表与目录结构，确认后投入使用
7. 当天日志记一篇搭建记录

## 模式 B：已有项目升级步骤

1. **硬性前置**：项目已有 `docs/` → 先整体 `mv docs doc` 原样保留（只改目录名、内容零改动、不用 git 命令；`doc/` 已存在则停下问开发者），新 docs 体系从零搭建，此后永不改动 `doc/` 内文件
2. **盘点**：Glob 全量文档 + 抽读关键文档，产出映射提案表——现有每份文档 → 体系位置（保留迁移 / 合并 / 原位保留）+ 缺失正本清单；二次开发场景同时提案 `docs/study/` 章节规划。判据：面向仓库访客的根目录文档（README、ARCHITECTURE、CONTRIBUTING 等）**原位保留**、不强制迁入 docs/，其内容可作 project.md 素材由开发者主导定稿；项目自有的设计/需求类文档才是迁移对象
3. **提案先行**：把映射表交给开发者批准，**不先动手**
4. 批准后执行：迁移用 `mv`（所有 git 操作由开发者自己执行），移动后修正全库路径引用；缺失正本按模板补建；确认 `.gitignore` 未忽略 `docs/`，已有则提请开发者移除
5. CLAUDE.md 接线（同模式 A 第 4 步）
6. **商讨模块 design.md 归属**（同模式 A 第 5 步）：接管/继续开发场景经开发者委托由 AI 起草/补全，开发者审核定稿
7. 当天日志记一篇迁移记录（迁移前状态 → 映射 → 动作，含 `docs/` → `doc/` 保留动作）
8. 接管别人代码库时，主动建议启动 study 学习笔记走读

## Common Mistakes

- **擅改 design.md**（最高红线：AI 永不擅改开发者需求正本，建议也需审核通过才落笔）
- 主动查阅问题疑惑区 / 临时草稿（只有被指名才读疑惑区）
- 归档时改名或删除文件；AI 自行判定废弃
- 日志创建时间靠估算而非 `date` 实取
- 在 `idea/` 里动开发者的文件
- 搭完骨架就收工，不主动商讨功能域划分与 design.md 归属；或新项目场景未经开发者落笔就代写 design.md
- 把来源项目的具体模块名、业务规则照搬进新项目——这套 skill 封装的是**机制**（权责、流程、归档），不是任何具体项目的内容
- 项目已有 `docs/` 时就地改建或覆盖，而不是先 `mv docs doc` 原样保留旧库再新建
- 把 `docs/` 写进 `.gitignore` 或默认不入库——文档库是要随远程仓库共同维护的，忽略规则必须提请开发者移除

## Red Flags - STOP

- 开发者还没批准映射方案就开始移动已有文档
- 想跳过 CLAUDE.md 接线「以后再补」
- 想顺手替开发者 add/commit/push——**所有 git 操作由开发者自己执行**
- 「这份文档没用了顺手删掉吧」——体系内文件永不删除，只归档
- 项目已有 `docs/` 却想清空、覆盖或就地改造成新体系——先整体重命名为 `doc/`，新体系另起 `docs/`
- 「docs 是本地笔记，顺手加进 .gitignore 吧」——文档库默认进远程仓库维护，禁止忽略
