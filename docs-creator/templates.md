# 文档库体系骨架模板

使用规则：以下模板是**骨架**，`<尖括号>` 为占位符；按目标项目的命名习惯与模块划分适配后落笔，示例性内容不得原样照搬。模板中机制条款源自体系正本，条款语义不改，仅适配名称与路径。

---

## 1. docs/project/README.md（spec/plan 存放与归档机制正本，AI 维护）

```markdown
# docs/project 内 spec/plan 存放与归档机制

brainstorming / 写计划会话产出的**设计记录（spec）与实施计划（plan）**按所属模块就地存放，不设独立集中目录。维护方：AI（机制正本即本文档；`CLAUDE.md` 文档体系表有对应条目）。

## 存放位置

| 文档所属 | 存放目录 | 示例 |
|---|---|---|
| idea 阶段模块（尚无正式 design.md） | `docs/project/idea/<模块>/` | `idea/<模块>/YYYY-MM-DD-<主题>-design.md` |
| 已立项模块 | `docs/project/<区域>/<模块>/` | `<区域>/<模块>/YYYY-MM-DD-<主题>-design.md` |
| 跨模块 / 全局改动 | `docs/project/全局/`（或对应区域目录） | `全局/YYYY-MM-DD-<主题>-design.md` |

- 文件命名：`YYYY-MM-DD-<主题>-design.md`（spec）、`YYYY-MM-DD-<主题>-plan.md`（plan）；日期前缀保证唯一，**归档不改名**。
- spec 与 plan 同目录混放（plan 头部 `**Spec:**` 字段互指），不设子分目录。
- `idea/` 目录维护权属开发者——AI 产出的 spec/plan 存于其中时**只动自己产出的文件**。

## 归档

落地或废弃后移入所属目录的 `archive/` 子目录（spec 与 plan 共用）：

| 判定 | 依据 | 动作 |
|---|---|---|
| 落地归档 | 状态行或日终日志明确记录「实施完成」（落地判定标准按项目约定：<默认 typecheck/构建通过即算，不等人工冒烟>） | 移入 archive/，状态行追加归档记录 |
| 废弃归档 | **开发者明确说**「废弃 / 被新设计取代」（AI 不自行判定废弃） | 移入 archive/，状态行标注「已废弃（原因）」 |
| 留守 | 待实现、会话进行中 | 不动 |
| 拿不准 | 依据不明 | 不动，报告开发者 |

配套规则：spec 落地归档时，其对应 plan（`**Spec:**` 字段指向该文档者）一并归档。模块升级路径：idea 阶段模块正式立项（design.md 迁入正式目录）时，其 spec/plan 一并迁入。

## 触发时机（全自动，无需开发者口令）

1. **写 / 追加日终日志时**——记录「实施完成」的那一刻就是归档时刻；
2. **写新 spec / plan 时**（清点其所属目录）。

开发者也可随时说「归档一下」触发即时清点（兜底）。

## 归档动作（固定四步）

1. `mv` 至所属目录的 `archive/`，文件名不变；
2. 文档顶部状态区追加一行：`- 已归档：YYMMDD 随 <功能> 落地`（废弃则 `- 已归档：YYMMDD 废弃（<原因>）`）；
3. 全库检索该文件旧路径，更新**活动文档**（模块 designs-specs、CLAUDE.md、本 README）中的路径引用；**历史日志（docs/log/）不改**，同批移动的关联引用顺手更新；
4. 当天日终日志记一笔。

## 回改通道

人工验收后若需回改已归档文档：直接在 archive/ 内改，或移回所属目录（状态行同步改回），日志记录。**归档只是位置变化，文件永不删除。**
```

## 10. 项目 CLAUDE.md 文档体系段（体系运转的关键接线）

写入项目根 `CLAUDE.md`（已有 CLAUDE.md 则并入），必备四块：

```markdown
## 文档体系与维护权责（最重要）

`docs/` 目录是开发者与 AI 共同维护的项目文档库，权责划分如下：

| 内容 | 维护方 | AI 的角色 |
|---|---|---|
| docs/project/<区域>/<模块>/design.md | 开发者主导 | 可提建议；经开发者审核通过才可修改，不得擅自改写 |
| docs/project/<区域>/<模块>/designs-specs.md | **AI 生成并维护** | 基于 design.md 严格生成，是开发的直接依据；开发者仅简单审核 |
| docs/project/project.md | 开发者主导 | 可建议；协助完善需审核通过 |
| docs/log/<YYMMDD>.md | AI | 每天一个开发日志；**每个小节标题下必须附创建时间行**（`> 创建于 YYYY-MM-DD HH:MM`，用 date 取实际时间） |
| docs/project/idea/ | **开发者** | AI coding 时不需要关注、不得修改（例外：AI 产出的 spec/plan 按机制存放于此，只动自己产出的文件） |
| docs/project/README.md | **AI** | spec/plan 存放与归档机制正本 |
| `docs/project/` 内各模块 spec/plan 文档 | **AI** | brainstorming/写计划产出，按模块就地存放；落地或废弃后移入所属目录 archive/（机制见 README.md） |
| docs/project/新功能开发区.md | **开发者** | AI 据此 brainstorming 立项并实施；完成后条目勾选并按轮归档 |
| docs/project/优化建议区.md | **开发者** | AI 据此实施优化；实施后按轮归档进归档区 |
| docs/project/问题疑惑区.md | **开发者** | **AI 不要主动查阅**，开发者指明时才阅读并答疑 |
| 各子目录同名说明 md（log.md / idea.md 等） | 随目录权责 | 目录功能与用法说明；新建子目录时随建随补 |
| docs/project/临时草稿（待写入）.md | **开发者** | **AI 不需要读取**；骨架由 AI 搭建时代建（模板见本文档第 12 节，条目全部留白），建后不再读取/修改 |

工作流程：开发者写 design.md → AI 据此生成 designs-specs.md → AI 按 designs-specs.md 开发。

## 全局硬性规则

<从 design.md / 样式规范中提炼的全项目硬性规则，逐条列出>

## Git 操作纪律（开发者指令）

- **禁止 AI 自主执行任何 git 操作**（add / commit / push / pull / checkout / reset 等全部命令）。
- 所有 git 操作由开发者自主完成；AI 最多在开发者明确要求时给出命令建议，不得代为执行。
```

> 注：Git 纪律块是文档库体系作者（开发者）的长期约定，默认写入；新项目开发者另有约定时按其口径改写。

## 11. <目录名>.md（每个子目录一份的目录说明）

docs/ 下每个子目录都配一份**与目录同名**的说明 md，说明该目录的功能作用与使用方式；新建子目录时随建随补，维护方随该目录的权责归属（开发者领地目录的说明文档 AI 不得擅改）。

```markdown
# <目录名>

<一句话：这个目录是做什么的。>

**使用方式**：<谁在什么情况下往这里放什么、文件如何命名、由谁维护。>

**边界**：<权责红线，如「AI 不读取本目录」「AI 只动自己产出的文件」等。>
```

> 示例口径——`log/log.md`（AI 维护：记录项目开发情况，每天一个 YYMMDD.md，小节附创建时间行）；`idea/idea.md`（开发者领地：想法草稿，AI 只动自己产出的 spec/plan）；`<区域>/<区域>.md`（区域说明 + 跨模块硬性规则，开发者主导）。

在 AI 实施或后期调整优化时，开发者随时可能想到新需求，但不适合当场写入需求正本（会干扰正在读取文档的 AI），也更适合放到下一轮处理（便于 git 提交区分每轮进度）。所以有了这个文档。它是完全的开发者文档，AI 不编辑、不读取。
