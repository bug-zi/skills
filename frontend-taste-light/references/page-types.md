# Page-Type Rules

Use this file before creating or substantially redesigning a frontend page. Pick the closest page type and let that type drive the composition.

## Landing Or Product Page

Purpose: explain, persuade, and move the user toward one clear next action.

Must do:

- Make the product, object, offer, or brand visible in the first viewport.
- Answer: what is it, who is it for, why now, and what action is next.
- Use real product screenshots, object photos, interface captures, or meaningful visual assets when possible.
- Keep one primary CTA. Secondary actions must be visibly quieter.
- Let the next section be hinted below the fold on common desktop and mobile viewports.

Avoid:

- Generic SaaS hero composition when the product has a more specific visual identity.
- Hero sections that say only abstract value propositions.
- Logo wall, testimonial strip, and feature cards before the product is understandable.

## Tool Or Web App

Purpose: let users operate, create, configure, inspect, or complete repeated work.

Must do:

- Start with the usable workspace, not a marketing hero.
- Prioritize controls, state, empty state, primary action, and feedback.
- Keep layout dense but calm. Make controls predictable and easy to scan.
- Give loading, empty, error, and success states for the main workflow.
- Keep repeated controls stable in size so hover, labels, and dynamic content do not shift layout.

Avoid:

- Decorative cards that slow down repeated work.
- Centered slogan-first pages unless the app genuinely has no usable state yet.
- Hiding core controls behind ornamental navigation or playful effects.

## Dashboard Or Admin

Purpose: support scanning, comparison, diagnosis, filtering, and action.

Must do:

- Use restrained color. Reserve strong color for status, alert, selection, or primary actions.
- Give metrics units, time ranges, source labels, and plausible loading/empty/error states.
- Make filters, date ranges, and drill-down paths clear.
- Charts must have labels, units, legends or direct labels, and accessible color choices.
- Keep tables and lists readable at realistic densities.

Avoid:

- Fake charts, fake user avatars, fake health indicators, or decorative data.
- Metrics without units or time windows.
- Fully centered layouts for operational screens.

## Portfolio Or Case Study

Purpose: make work, taste, process, and outcomes legible.

Must do:

- Use project-specific visuals, artifacts, outcomes, and process evidence.
- Allow stronger typography and composition, but preserve readability.
- Show the object of work early: screenshot, product surface, artifact, result, or case-study image.
- Structure around problem, role, process, result, and proof when possible.

Avoid:

- Generic capability cards that could describe any designer or developer.
- Decorative mockups that hide the actual work.
- Overly cinematic layouts that make project details hard to inspect.

## Content Site Or Editorial Page

Purpose: support reading, navigation, credibility, and retention.

Must do:

- Keep text measure readable and hierarchy steady.
- Use navigation and section anchors when content is long.
- Make images, diagrams, code blocks, and quotes serve the argument.
- Preserve source clarity for factual claims.

Avoid:

- Hero treatment that delays the actual content.
- Decorative cards for every paragraph.
- Low-contrast body text or oversized display type inside dense sections.

## Game Or Interactive Experience

Purpose: let the user understand the state, interact immediately, and feel the system respond.

Must do:

- Put the playable or interactive surface first.
- Make controls, state, score/progress, and feedback visible.
- Use visual style to support the game world or interaction model.
- Keep layout stable across viewport sizes.

Avoid:

- Marketing-first landing pages when the user asked for a game or interactive tool.
- Decorative UI that competes with gameplay or primary interaction.
