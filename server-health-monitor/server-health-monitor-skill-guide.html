01 这是什么

server-health-monitor 是一份用于服务器运行健康巡检的 Codex skill。它的目标不是“随便扫一眼服务器”，而是把授权范围内能采集到的证据，整理成中文、可审计、能交给管理人员阅读的正式报告。

1
核心定位

只读巡检：默认不改配置、不安装组件、不登录登出、不做破坏性操作。

2
主要对象

浙音 zheyin、杭电 hdu 的 doops 托管节点，以及用户提供的服务器清单。

3
最终产物

HTML、PDF、Markdown、JSON、质量审计和交付清单，而不是一段临时命令输出。

对小白来说，最重要的一句话是：这份 skill 不是“万能监控系统”，它是“证据型巡检报告生成器”。能证明什么，就写什么；没采集到什么，也必须写清楚。

02 什么时候用

当用户提供服务器清单、主机列表、运维资产表、doops 目标，或直接说“帮我看浙音/杭电服务器运行状态”时，就适合使用这份 skill。

用户说法 你应该理解成 默认处理方式
“检查浙音服务器状态” / “zheyin 巡检” 先看 zheyin doops 节点自身健康 走 doops-only 自身节点路径，不要先要 SSH 密码
“检查杭电 hdu 状态” 先看 hdu doops 节点自身健康 同样走 doops-only 自身节点路径
“这是服务器 Excel，帮我巡检” 用户提供了普通服务器资产清单 先导入清单，可做网络探测；深度主机指标需明确授权
“只看哪些还在用，哪些能监控” 需要清单分层分类 使用 --classify-inventory 生成 active / inactive / monitorable 分组
“和上次报告对比” 需要趋势比较 给 runner 加 --previous-report

03 先记住的模型

这份 skill 的工作流可以拆成五个动作：定对象、采证据、判边界、出报告、做审计。

定对象

先确认要检查的是 doops 节点自身，还是 Excel / JSON / CSV 里的一批普通服务器。对象不同，证据含义完全不同。

采证据

默认使用 doops 的 targets、info、workspace exec、read、clean。对于 zheyin/hdu 自身节点，不需要 SSH、WinRM 或 SNMPv3。

判边界

CPU、内存、磁盘、负载、进程、服务是主机级证据；端口探测只是网络可达性证据。报告必须把这两类证据分开。

出报告

正式报告必须是中文，并且要有 HTML、PDF、Markdown、JSON、导览图状态、质量审计和交付清单。

做审计

交付前检查质量审计和文本完整性，尤其看是否有乱码、英文标题、敏感信息、空导览图和证据边界缺失。

04 最常用跑法

以下命令假设你在 skill 根目录：C:\Users\Administrator\.codex\skills\server-health-monitor。PowerShell 里先设置 doops 网关兼容开关，再运行采集与报告生成。

浙音 zheyin 自身节点健康巡检

$env:DOOPS_ALLOW_INSECURE_GATEWAY='1'
python scripts/collect_doops_inventory.py --environment zheyin --out reports/zheyin-self-node/inventory.json
python scripts/run_server_health_monitor.py --inventory reports/zheyin-self-node/inventory.json --out reports/zheyin-self-node

这条路径会采集 zheyin doops 节点自身的 CPU、内存、磁盘、负载、在线状态、主要进程和关键服务。它不能证明 Excel 清单里所有普通业务服务器的主机健康。

杭电 hdu 自身节点健康巡检

$env:DOOPS_ALLOW_INSECURE_GATEWAY='1'
python scripts/collect_doops_inventory.py --environment hdu --out reports/hdu-self-node/inventory.json
python scripts/run_server_health_monitor.py --inventory reports/hdu-self-node/inventory.json --out reports/hdu-self-node

先做 doops 预检

$env:DOOPS_ALLOW_INSECURE_GATEWAY='1'
python scripts/collect_doops_inventory.py --preflight --environment zheyin
python scripts/collect_doops_inventory.py --preflight --environment hdu

预检只看 doops CLI、目标、网关和简短诊断，不运行远端采集。预检失败时应停止，不要编造主机指标。

用脱敏样例跑离线演示

python scripts/run_server_health_monitor.py --inventory assets/samples/zheyin-inventory.example.json --out reports/zheyin-sample --offline

离线样例适合看报告长什么样，但不能当成真实服务器状态。

从 Excel 清单做网络探测

python scripts/collect_doops_inventory.py --inventory path/to/servers.xlsx --probe-target zheyin --limit 30 --out reports/zheyin-excel/inventory.json
python scripts/run_server_health_monitor.py --inventory reports/zheyin-excel/inventory.json --out reports/zheyin-excel

这会从 doops 所在网络视角探测清单中的地址和端口。注意：网络探测不能替代 CPU、内存、磁盘等主机指标。

有授权时采集普通服务器主机指标

python scripts/collect_doops_inventory.py --inventory path/to/servers.xlsx --probe-target zheyin --host-metrics --host-metrics-target zheyin --host-metrics-profile zheyin-monitor --limit 30 --out reports/zheyin-excel-hostmetrics/inventory.json
python scripts/run_server_health_monitor.py --inventory reports/zheyin-excel-hostmetrics/inventory.json --out reports/zheyin-excel-hostmetrics

这是扩展路径，不是 zheyin/hdu 默认路径。它依赖 doops 采集节点上已经准备好的只读监控账号或配置，不应该从 Excel 中直接抄密码。

05 输入清单怎么准备

这份 skill 支持 JSON、CSV/TSV 和 Excel。小白最容易混淆的是“清单字段”和“真实证据”：清单里的字段只是声明，只有采集到的观察结果才是运行证据。

最小 JSON 结构

{
  "environment": {
    "name": "示例环境",
    "inspection_window": "2026-05-15 10:00-11:00"
  },
  "servers": [
    {
      "name": "web-01",
      "address": "10.0.0.10",
      "os_type": "linux",
      "role": "web",
      "business_system": "统一门户",
      "ports": [22, 443]
    }
  ]
}

常用字段说明

字段 新手理解 注意事项
name 服务器显示名称 必填，报告矩阵会用它识别对象
address IP 或主机名 做 live 检查时通常需要
doops_target doops 目标名 doops 采集时优先级最高
os_type 系统类型 可填 linux、windows 或 unknown
role 业务角色 比如 web、database、file service，用于理解影响
lifecycle_status 是否还在使用 配合 --classify-inventory 做活跃/停用分组
ports / port_obligations 应该检查的端口 显式业务端口不可达比推断的管理端口不可达更严重
metrics CPU、内存、磁盘等观测指标 如果是外部填入，要能说明来源
collection_errors 采集失败原因 只能写脱敏类型，不写密码、Token 或原始 stderr
Excel 资产表里可能有账号、密码、负责人、部门等字段。正式报告不展示长期缺失或敏感字段；凭据必须转成脱敏引用，不得写进报告、JSON、Markdown 或聊天内容。

清单分类会生成什么

当使用 --classify-inventory 时，采集器会先把全部记录分成仍在使用和停用，再把仍在使用的服务器分成可监控和不可监控，并在 inventory.json 旁边写出四个 CSV：

  • inventory-active-servers.csv：仍在使用的服务器。
  • inventory-inactive-servers.csv：停用或不再使用的服务器。
  • inventory-monitorable-servers.csv：成功采集 CPU/内存等主机指标的服务器。
  • inventory-unmonitorable-servers.csv：当前无法采集主机指标，需要补授权、补地址或复核的服务器。

06 证据边界怎么看

健康报告最怕“证据过度解读”。这份 skill 明确要求：缺什么证据，就写什么边界，不能把网络可达说成主机健康，也不能把 doops 节点自身健康说成全部业务服务器健康。

覆盖标签 说明 不能误解成
doops-self-collected 直接从 doops 目标节点自身采到 CPU、内存、磁盘、负载、进程、服务。 不能说 Excel 里所有普通服务器都被采了主机指标。
doops-network-probe 从 doops 内网视角探测地址或端口是否可达。 不能说数据库、应用进程或磁盘一定健康。
ssh-collected / winrm-collected 通过只读 SSH 或 WinRM 采集普通服务器主机指标。 不能暴露账号、密钥、命令行参数或原始失败日志。
snmp-collected 通过 SNMPv3 采集 CPU、内存、磁盘、在线时长等指标。 通常不能等价为服务和进程状态完整可见。
partial-host-metrics 主机指标只采到一部分，或部分服务器失败。 不能把失败项当作健康；应写“无法监测”与脱敏失败类型。
对 zheyin/hdu 的默认自身节点检查，不要主动要求用户提供服务器 IP、SSH 密码、WinRM 密码或 SNMPv3 密钥。doops 已经是采集通道。只有用户明确给普通服务器清单并要求深度采集时，才进入 SSH/WinRM/SNMPv3 扩展路径。

07 交付物在哪里

报告不是只交一个 PDF。正式交付包必须能被人阅读、复核、归档和机器处理。

单次巡检入口

delivery/final-report.html 是优先打开的 HTML 报告。PDF、Markdown、JSON、导览图状态、质量审计和交付清单都在同一个 delivery/ 目录。

批量巡检入口

delivery-batch/index.html 是批量报告首页；delivery-batch/servers/index.html 是单服务器报告索引。不要让用户直接进 delivery-batch/servers/ 原生目录找文件。

单次报告必须包含

文件 作用
delivery/final-report.html正式可读 HTML 报告。
delivery/final-report.pdf便于发送、归档和打印的 PDF。
delivery/final-report.md精简 Markdown 版本，便于复制和系统归档。
delivery/final-report.json结构化证据和高级报告模块，便于程序复核。
delivery/guide-image-status.json记录导览图是 AI 生成、复用还是 HTML/CSS 备用。
delivery/quality-audit.md人类可读的质量审计结果。
delivery/delivery-manifest.md交付清单和入口说明。

管理人员最先看哪几块

  1. 管理结论：当前是否健康、风险等级、需要谁处理。
  2. 核心指标：CPU、内存、磁盘、负载、进程覆盖情况。
  3. 关键服务：服务状态是否采到，未采集要写清楚。
  4. 服务器矩阵：每台服务器的状态、优先级、处理时限和证据边界。
  5. 问题与建议：证据、业务影响、处置建议和建议时限。
  6. 趋势与边界：是否有上一期对比，本次无法证明什么。

08 质量与安全规则

这份 skill 的质量要求很硬：正式报告必须中文、必须有导览图、必须有质量审计、必须保护秘密、必须把证据边界写明。

中文与可读性

  • HTML、PDF、Markdown、导航、表头、管理结论和证据解释都必须使用中文。
  • 不要出现 Management Summary、Findings、Technical Evidence 这类英文正式标题。
  • 不得出现乱码、连续问号、Unicode replacement character 或明显 mojibake 片段。

导览图规则

  • 报告表头必须有 GPT/AI 导览图，或经过用户确认后的中文 HTML/CSS 备用导览图。
  • 导览图区域不能留空，失败原因只写进 guide-image-status.json，不要写进正式报告正文。
  • 当覆盖类型是 doops-self-collected 时，导览图必须明确这是 doops 节点自身状态监测，不能暗示已覆盖其他普通业务服务器。

敏感信息

  • 不要打印、保存或报告真实密码、Token、Cookie、私钥、API Key、网关密钥或 doops 凭据。
  • SNMPv3、WinRM、SSH 的密钥和密码只能留在授权采集节点的本地秘密文件或环境中，不能写进清单或报告。
  • 失败日志只保留脱敏类型，比如 ssh-auth-or-command-failed、snmp-timeout、invalid-address。

09 常见问题

预检失败怎么办

先看 --preflight 的脱敏 JSON，确认 doops CLI、目标名、网关和 targets 状态。预检失败时停止，不要继续跑 exec，更不要编造 CPU 或内存数据。

报告生成时提示没有 AI 导览图怎么办

默认 auto 模式不能静默降级到 HTML/CSS。如果没有可用的内置 AI 生图能力或本地 API Key，需要询问用户是否提供 API Key，或是否明确接受 HTML/CSS 备用导览图。确认后再用相应模式重跑。

Excel 里有密码，能直接用吗

默认不能。Excel 密码字段应被脱敏处理。普通服务器深度指标建议使用 doops 采集节点上预先准备的只读 monitor 配置，而不是把 Excel 密码写进输出。

端口不通就是严重故障吗

不一定。显式声明的业务或服务端口不可达可以是严重证据；从操作系统或 Excel 推断出来的 SSH/RDP 管理端口不可达，更常见是预警和需复核，因为它可能被堡垒机、防火墙策略故意限制。

为什么批量报告还要生成单服务器索引

因为正式交付要给读者一个设计过的入口。delivery-batch/index.html 看总体，delivery-batch/servers/index.html 找单台服务器，避免用户直接打开原生目录。

没有上一期报告怎么办

报告应写明“本次为基线巡检，暂无趋势对比”。不要假装有新增、恢复或持续问题。

10 交付前清单

每次准备交付前，用下面这张表快速复核。它比“看起来正常”可靠得多。

检查项 通过标准
报告入口 单次有 delivery/final-report.html；批量有 delivery-batch/index.html 和 delivery-batch/servers/index.html。
交付完整性 HTML、PDF、Markdown、JSON、guide status、quality audit、manifest 都存在。
中文质量 正式报告标题、导航、表头、结论均为中文，无乱码和英文正式模块标题。
证据边界 清楚说明采集对象、覆盖标签、未采集项和不能证明的范围。
敏感信息 没有真实密码、Token、Cookie、API Key、私钥、SNMP 密钥或原始凭据日志。
质量审计 quality-audit.json 的关键检查为 pass，quality-audit.md 可读。
最终说法 不把网络探测当主机健康，不把 doops 自身节点健康当所有业务服务器健康。
新手最稳的交付顺序：先打开 HTML 看报告正文，再看 PDF 是否存在，再看 quality-audit.md，最后用 delivery-manifest.md 对照所有入口是否齐全。

doops 一种受控的远端执行和采集通道，用来替代直接 SSH 登录的入口。
